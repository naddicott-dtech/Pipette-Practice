## 0. Source-code orientation (read before testing)

Quick read of `src/` to set expectations for what the UI _should_ do:

- **Tech stack:** Vite + React 19 + react-three-fiber + zustand + Tailwind. Single-page 3D scene, no routing.
- **Workflow state machine** (`src/store.ts`): `GET_TIP → INTAKE_SAMPLE → LOAD_WELL → RUN_GEL → COMPLETE`.
- **Inputs:**
  - Mouse moves the pipette in XZ (raycast onto y=0 plane).
  - **SPACE held** lowers the pipette. ~300 ms ramp to fully lowered; ~600 ms = puncture.
  - **Plunger slider** (vertical, rotated `<input type="range">`) appears only when over the correct target.
- **Targets:** Tip rack at world `(-5, 0, 2)` r=1.5; sample tubes near `(-3..-0.6, 0, 2.5)` r=0.45; gel wells near `(0.6..4.2, 0.05, 0.5)` r=0.6; trash at `(-5, 0, -2)` r=1.0.
- **Failure modes defined** in `store.ts`: `PUNCTURE`, `OVERFLOW`, `EMPTY_EJECT`, `NO_TIP`. But `UIOverlay.tsx` only renders copy for **PUNCTURE / OVERFLOW / NO_TIP** — **`EMPTY_EJECT` has no message**.
- **Documented hard-stop / soft-stop semantics** in `PLAN.md` and `CLAUDE.md`: soft stop = 0.7, hard stop = 1.0.
- **Test scaffold** in `src/sim/rules.test.ts` is mostly `it.todo` — i.e., the "rules" layer is documented but **not yet implemented**. The current behavior lives directly in `UIOverlay.handlePlungerChange` and `InteractionDriver`, which already hints at fragility (no single rules layer, two places mutate workflow).
- **README** is the unedited AI Studio boilerplate ("My Google AI Studio App") — has no user-facing instructions.

### Known smells flagged from code-read alone (to verify in browser)

1. **`UIOverlay.handlePlungerChange` advances `INTAKE_SAMPLE → LOAD_WELL` only when `val === PLUNGER.REST` exactly.** The slider snaps in 0.01 steps, so this _can_ work, but it's a brittle exact-equality check on a float that comes from `parseFloat(e.target.value)`. Slightly miss zero and you stall.
2. **`LOAD_WELL → RUN_GEL` triggers as soon as `liquidInTip < VOLUME.EMPTY_EPS * 2` (= 0.1).** That fires after a single well is dispensed. But `WORKFLOW.WELL_COUNT = 4` and `LabObjects` shows 4 sample tubes / `GelBox` shows 4 wells. The state machine appears to **skip the multi-well loop entirely** — there is no `tryDiscardTip` step in the live workflow, no per-well loop counter, and no transition that returns to `GET_TIP` after a well is loaded.
3. **`InteractionDriver.onKeyDown` calls `setPlunger(0)`** on every Space press. So if you draw liquid, lift Space briefly, then re-press Space, the plunger snaps back to 0 — but `liquidInTip` is preserved. This is probably fine but worth checking: does the user perceive Space as "reset" or "lower"?
4. **No discard / no trash interaction** is wired in `InteractionDriver` despite a `TRASH` target being defined. So the educational "always discard the tip between samples" lesson is absent.
5. **`Band` component creates a `setInterval` per band per well** in `GelBox.tsx`. CLAUDE.md explicitly warns against this. Not a user-visible bug yet, but a leak risk if reset is repeatedly hit during RUN.
6. **No reset hook for `setHasTip(false)`** on `reset()` — actually `reset()` does set `hasTip: false`. Good. But the "Try Again" button in the failure modal only calls `reset()`; that's fine.
7. **No camera/zoom controls.** The scene is fixed orthographic-ish via `CameraRig`. First-time users with a klunky pipette experience may want to zoom for precision.
8. **Mobile warning:** there's a "use a larger screen" banner. Confirms author knows touch isn't supported. No alternative input for tablets.

These are pre-test hypotheses; the rest of the doc verifies them in the live build and adds anything new the live test surfaces.

## 2. Workflow walkthrough

### 2.1 Step 1 — `GET_TIP` (Pick up a fresh tip)

**Repro:** With cursor positioned over the tip rack (screen ~(400, 305) in 1492×697 viewport, world ≈ (−5, 0, 2)), dispatch `keydown(Space)` and hold for ≥300 ms.

**Expected:** Pipette lowers, tip is acquired, store advances `GET_TIP → INTAKE_SAMPLE`, instructions update to "Move to the DNA tube...".

**Actual:** "PIPETTE LOWERED (SPACE HELD)" badge appears, but `hasTip` stays `false` and the workflow does **not** advance. Tip rack is no longer in the camera frame by the time `lowered=true`.

#### Root cause (verified against source)

`CameraRig` blends OVERVIEW `(8,8,12)` → CLOSEUP `(2,2,6) lookAt (0,0,0)` driven by `loweredDepth` (0..1). `InteractionDriver`'s tip-pickup gate requires `hover.kind === 'tip-rack' && lowered === true`. `lowered` only becomes true at `depth >= 1` (≈300 ms hold). At that moment, the camera is ~85% of the way to CLOSEUP, which is framed on the gel and the closer sample tubes. The tip rack at world `(−5, 0, 2)` is **off-screen left** in CLOSEUP framing, so no screen-space cursor position projects onto its hover circle (Manhattan radius 1.5).

I retried by chasing the cursor leftward as the camera zoomed (cursor moved to `(50, 400)`, the screen-left edge). Still misses — the leftmost world point reachable in CLOSEUP is roughly `x ≈ −2`, well outside the tip-rack radius.

**Severity: P0 — blocks the very first step of the simulation.** A first-time user has no path through the lesson without already knowing about this and either (a) frantically chasing the cursor, (b) using the keyboard timing of "press → release → press just barely" to keep depth < 1 (which also doesn't pick up the tip), or (c) being told "this is broken, advance it manually." None of those are acceptable in an instructional sim.

**Suggested fixes (ranked):**
1. **Decouple camera zoom from `loweredDepth` for tip pickup.** Either keep OVERVIEW for the whole `GET_TIP` step, or zoom toward the *current hover target's* position rather than a fixed `(0,0,0)` lookAt. The latter is the correct general fix and benefits sample/well steps too.
2. **Make CLOSEUP follow the cursor** (lookAt = `pointer.x, 0, pointer.z`) instead of a hard-coded `(0,0,0)`. That keeps whatever you started over still under the cursor after the zoom.
3. **Cheat fix:** In `InteractionDriver`, use a "latched" hover — capture the hover target at the moment Space is first pressed, and accept the tip-pickup if the latched hover was `tip-rack` and the user holds long enough, regardless of where the cursor lands during zoom.

#### Secondary issues observed during the same test

- **`Empty` label position drifts wildly.** It's an `<Html>` block at offset `(0.5, 0, 0)` from the pipette mesh. As the pipette descends and the camera zooms, the label slides across the screen (top-center → middle-left). It also overlaps the instructions card at certain camera angles. P2.
- **Cursor ring stays green** even though the tip-pickup attempt is failing (`hasTip` stays false). The ring's "ready" color logic only checks `step === GET_TIP ? !hasTip : hasTip`, so it tells the user "you're ready" right up until success — but never tells them *what to do* when nothing happens. P2; users will just press space repeatedly with no feedback.
- **Tip rack glow ring (gold)** is correctly drawn, but it's a static ring around the rack. It does not pulse or change when the pipette is lowered "near it but not on it," so there's no proximity hint. P3.

### 2.2 Step 2 — `INTAKE_SAMPLE` (Draw DNA from a tube)

**Setup for this section:** Because step 2.1 blocks the natural flow, I forced `hasTip=true` and `step='INTAKE_SAMPLE'` via direct zustand store mutation (the snapshot setter closures still drive the live store) so that downstream steps could be exercised. All findings below are reproducible from this seeded state.

#### 2.2.1 Hover hit-box for sample tubes is very small

`SAMPLE_TUBES[*].radius = 0.45` (Manhattan). Translating to screen-pixels at the OVERVIEW camera, the hover circle for DNA 1 spans roughly **30 px** in the visible UI. To activate `hover.kind='sample'`, my cursor had to land within ~3 px of the projected tube center `(479, 363)`. Cursor positions a few pixels off (e.g. `(475, 345)`) gave `hover=null` even though the ring visually looked "on" the tube.

Compare with the tip rack: `radius=1.5` → ~85 px on-screen. Much more forgiving.

**Severity P2.** Klunky in normal play. Either:
- Increase `SAMPLE_TUBES.radius` to ~0.75 (roughly the visible cube + cylinder footprint), or
- Render a hover-affordance ring on every tube (today only DNA 1 gets a purple alignment ring), or
- Use Euclidean instead of Manhattan distance and bump radius accordingly.

#### 2.2.2 Same camera-zoom-loses-target bug

Identical pattern to 2.1. With cursor on DNA 1 (`hover.kind='sample'`, plunger UI shown), I dispatched `keydown(Space)`. After 1 s:

- `isLowered=true`, `lowerDepth=1` ✓ (lowering works)
- `hover=null` (camera moved → cursor world point shifted from `(−3, 0, 2.5)` to `(−1.10, 0, 0.60)`)
- The plunger UI **disappeared entirely** because `showPlunger` requires `isNearSample` to be true.

**This is the dominant user-facing klunkiness.** The instruction says "Hold SPACE to lower the tip. Drag the plunger…" but the plunger panel vanishes the instant Space is pressed. The user is stuck holding Space with no visible control to drag.

**Severity P0.** Same root cause as 2.1; the suggested fix in 2.1.1 (camera lookAt = current pointer or current hover target) resolves both 2.1 and 2.2 in one shot.

#### 2.2.3 Plunger control state is "ready but disabled" with no explanation

When `isNearSample=true` but `isLowered=false`, the plunger panel renders with a translucent overlay reading **"Hold Space to unlock plunger."** The text overlaps the **"SOFT STOP (70%)"** label, making both partially unreadable (visible in screenshot — the words run on top of each other). P2 polish.

#### 2.2.4 Plunger orientation is non-obvious

The plunger uses `<input type="range">` rotated −90°, sitting inside a 256 px-wide black panel that says PLUNGER, REST, SOFT STOP, HARD STOP. The thumb is the small white circle. **There is no arrow, gradient, or tactile hint** that this is a vertical drag from REST (top) → HARD STOP (bottom). A first-time user is going to look for a horizontal slider or a button. The marker labels say REST / SOFT STOP / HARD STOP but they sit on opposite sides of the rotated rail and don't visually align with the thumb's travel. P2.

Suggested fix: replace the rotated-`<input>` hack with a custom drag-handle (see "klunky" laundry list at end). At minimum, add an animated up/down arrow on the thumb and color-code the SOFT/HARD zones on the rail.

#### 2.2.5 Intake transition uses exact-equality on a float

`UIOverlay.handlePlungerChange`:
```js
if (val === PLUNGER.REST && liquidInTip > VOLUME.FULL - 0.2) {
  setStep(WorkflowStep.LOAD_WELL);
}
```

`PLUNGER.REST = 0`. The slider step is `0.01`, so `parseFloat('0')` does equal `0`, but if the user releases at e.g. `0.01` the transition silently never fires. They've drawn liquid, the slider is "almost back to rest," and the workflow stalls. P2 reliability.

Suggested fix: `val <= PLUNGER.REST + 0.02` (or define an `EPS`).

### 2.3 Step 3 — `LOAD_WELL` (Eject DNA into a well)

**Setup:** Forced `step='LOAD_WELL'`, `hasTip=true`, `liquidInTip=1`. Hovered the cursor over well 0 at projected screen `(797, 382)`.

#### 2.3.1 Same camera-zoom-loses-target bug — but this one matters less

Cursor over well 0 → `hover={kind:'well', index:0}` ✓. Held Space for 2 s. After camera zoomed:

- `isLowered=true`, `lowerDepth=1` ✓
- `hover=null`, `activeWellIndex=null` (cursor world point shifted from `(1.14, 0.41)` to `(0.37, 0.39)`)
- **No `PUNCTURE` failure fired**, even though `holdMs > 600` exceeded `LOWER_HOLD_PUNCTURE_MS`. Reason: `InteractionDriver` requires `hover.kind === 'well'` for puncture, and hover was null by then.

So the puncture failure is also functionally unreachable. Same root cause as 2.1 / 2.2.

This step is *less* user-blocking than the others because the wells happen to sit near the CLOSEUP camera's lookAt `(0,0,0)`, so well 0 is *visually* close to where the cursor lands after zoom. With small mouse adjustments mid-zoom you can probably keep `hover='well'` more easily than for the tip rack. Still klunky. Severity P1.

#### 2.3.2 Workflow advances to `RUN_GEL` after one well, despite four wells/tubes existing

This is the bug I flagged from code review and it reproduces:

- Forced `step=LOAD_WELL`, `hasTip=true`, `liquidInTip=1`, `activeWellIndex=0`.
- Simulated a single complete eject (`addDnaToWell(0, 1)`, `setLiquid(0)`).
- Workflow auto-advanced to `RUN_GEL`. Instructions read **"The wells are loaded!"** — but `dnaInWells = [1, 0, 0, 0]`. Only one well is loaded.
- Pressing `START POWER SUPPLY` proceeds to `COMPLETE`. The visible band animation only happens for well 0; wells 1–3 stay empty (no bands).

**Severity P0 for instructional integrity.** The "lab" sets up four samples (DNA 1–4) and four wells, but the simulated workflow never asks the user to load more than one. The teaching goal of "load each lane separately" is silently dropped. The `rules.test.ts` scaffold actually planned a `tryDiscardTip` step plus a multi-well loop (`if n<COUNT: GET_TIP else RUN_GEL`) — that work is unstarted.

**Suggested fix:**
1. After a successful eject into well `n`, transition to a `DISCARD_TIP` step (over `TRASH` target).
2. After successful tip discard:
   - if `n + 1 < WORKFLOW.WELL_COUNT` → `setStep(GET_TIP)`, `setActiveTube(n+1)` (each tube → its own well).
   - else → `RUN_GEL`.
3. Highlight the next sample tube and next well to disambiguate which goes where (cross-contamination is the whole point of fresh tips).
4. The `DNA n` tubes should also be claimed/locked once used — visually ghosted to communicate "you've used this one."

#### 2.3.3 Only DNA 1 has a proximity ring; DNA 2/3/4 have none

`LabObjects.tsx` only renders the alignment ring for `tube.index === 0`. So during `INTAKE_SAMPLE` the user has no visual hint where to draw from for samples 2–4. (Today this is moot because the workflow skips them, but if you fix 2.3.2, this will become a real bug.)

Suggested fix: render the alignment ring around the *current target* tube, driven by an `activeTubeIndex` from the store.

### 2.4 Step 4/5 — `RUN_GEL` and `COMPLETE`

**Setup:** Workflow auto-advanced from `LOAD_WELL` after one eject (see 2.3.2).

- Click handler for "START POWER SUPPLY": works on first click; sets `isBoxOn=true` and `setStep(COMPLETE)` simultaneously, so there is no visible **running** state — it goes straight from "ready" → "complete." The success copy ("Loading Successful! The DNA is separating by size") then sits indefinitely. P2 — there's no closure to the "running" beat, no time-based animation gate; the user can't actually *watch* the bands separate vs. just see them already separating.
- Band rendering: `Band` components use `setInterval(50ms)` to migrate. **CLAUDE.md explicitly says do not do this**, prefer `useFrame`. Each band leaks an interval until the component unmounts (which only happens on a reset that drops the well's DNA below 0). Currently 4 bands × 1 well = 4 intervals; if the multi-well fix lands, that's 16. Not user-visible yet, but a known foot-gun. P3.
- Bands themselves are very small (`0.7 × 0.02 × 0.1`) and the same dark purple as the loaded well — they're hard to see at the OVERVIEW camera. A first-time user will not understand "the bands are separating." P2.
- The polarity labels (`+` / `−`) on the gel chamber are just colored glyphs — no text legend. A teacher would want to point at the sign and say "smaller fragments migrate this way" — the labels need an associated arrow or a "Smaller →" caption. P2 polish.

Mapping enum → wired trigger → UI message:

| Failure        | Trigger wired? | Has UI string? | Verified in browser              |
| -------------- | -------------- | -------------- | -------------------------------- |
| `PUNCTURE`     | Yes (Driver)   | Yes            | Cannot reach via real input due to camera-zoom bug. Modal renders correctly when forced. |
| `OVERFLOW`     | **No**         | Yes            | Modal renders if forced; never fires from gameplay. |
| `NO_TIP`       | **No**         | Yes            | Modal renders if forced; never fires from gameplay. |
| `EMPTY_EJECT`  | **No**         | **No**         | Forced; modal renders **with NO description text**. |

Severity P1: the failure system is half-built. The teaching value of "see what goes wrong if you do X" is unrealized.

When a failure modal is dismissed via "Try Again", `reset()` correctly clears `hasTip`, `liquidInTip`, `dnaInWells`, etc. ✓

#### 2.5.1 Failure modal title is generic; should name the technique error

Today the modal header is always **"Technique Error!"** with the body sentence varying per failure. For an instructional sim, the *title* should specify which technique was missed, so students can immediately scan and know which step they fumbled. Right now the diagnostic info is buried in body copy and missing entirely for `EMPTY_EJECT`.

Suggested copy:

| Failure         | Title (what failed)                | Body (why it matters / how to fix)                                                                 |
| --------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------- |
| `PUNCTURE`      | "Punctured the gel"                | "You held the pipette down too long over the well. Lower just to the gel surface, not through it." |
| `OVERFLOW`      | "Ejected above the well"           | "The pipette was too high when you pushed the plunger. Lower fully into the well before dispensing." |
| `NO_TIP`        | "No tip on the pipette"            | "You touched the sample without a fresh tip — that's a cross-contamination hazard. Pick up a tip first." |
| `EMPTY_EJECT`   | "Ejected with an empty tip"        | "Your tip had no liquid when you pushed the plunger. Draw the sample to the soft stop first." |
| `HARD_STOP_TO_DRAW` | "Drew past the soft stop"      | "Pushing past the soft stop while drawing creates bubbles. Press only to the *soft* stop, then release to draw." |
| `SOFT_STOP_TO_EJECT` | "Stopped at the soft stop"    | "You only ejected the main volume. Push all the way to the *hard* stop to expel the residual." |

Implementation note: store both `title` and `body` per `FailureMode` (an object map, not separate ternaries in JSX). Add a third optional field `hint` that, on a second consecutive failure of the same type, expands the modal with a short "Try this:" tip — graduated scaffolding for struggling students.

Severity P1 (bumped from P2 because this directly limits the simulator's teaching value, which is its whole purpose).

### 2.6 Trash receptacle is an invisible interaction zone

`TRASH` target is defined at world `(−5, 0, −2)` with radius `1.0`, registered in `InteractionDriver.TARGETS`, and `hover.kind='trash'` returns from `findHover`. **But there is no mesh for it in `LabObjects.tsx`** and **no rule consumes the trash hover anywhere in the live driver.** It's a phantom hit-zone.

Severity P3 today (no consequence), but if/when 2.3.2 is fixed and discard becomes a step, you'll need both a mesh and a rule. Also: an unmarked clickable area near the tip rack is potentially confusing during exploration.

## 3. UI / overlay issues (cross-cutting)

- **"Empty" / volume label** is rendered via `<Html>` at `(0.5, 0, 0)` offset from the pipette mesh. This means it sits in **world** space and tracks the pipette across the screen. It overlaps the instructions card at the OVERVIEW camera, drifts to the middle of the screen at CLOSEUP, and reads `Empty` even before the user understands what it refers to. P2.
  - Fix: render volume in the bottom-right HUD (or pinned next to the plunger panel). Don't world-space it.
- **Instructions card** doesn't change visually when the step transitions. Same dark card, same icon. The user can miss that the step advanced. P2 — at minimum, fade-in a "Step 2 of 5: Draw Sample" header.
- **Reset button** is a small unlabeled circular icon in the top-right corner. New users will not realize it's a reset. P3.
- **No undo for a single step.** Reset is all-or-nothing — punctured a well? Start the entire lab over. For an instructional sim, "let me try just *that step* again" is valuable. P2.
- **No tutorial / first-time hint overlay.** The instructions card is the only guidance. Specifically there's no "Use mouse to move pipette, hold Space to lower" callout on first load. P2.
- **Camera is not user-controllable.** No orbit, no zoom in/out, no reset-camera. For an interactive 3D scene this is jarring. P3.

## 4. Plunger mechanic — constructive critique and alternatives

You flagged this directly. Here's what's not working and three concrete redesigns to consider.

### 4.1 Why the current mechanic feels klunky

1. **Mode-switched verb that the user doesn't know they're in.** The same drag does *intake* (in `INTAKE_SAMPLE`) and *eject* (in `LOAD_WELL`), but the slider has no visual difference between modes. A user who learned "drag down then release to suck up" has no reason to expect "drag down again to push out."
2. **Real-pipette analogy is half-honored.** A real micropipette has a discrete two-stop plunger: press to soft stop to draw, press past soft stop to hard stop to fully eject. The slider exposes a continuous 0–1 with markers at REST / SOFT / HARD, **but the success criteria are exact-equality at REST and a "drag past 70%" gate**. The continuous control invites continuous nudging; the gates punish that.
3. **Vertical slider is implemented as a `<input type=range>` rotated 90°.** Drag direction is ambiguous (mouse-down = up or down?). `accent-blue-500` colors the filled portion but along the *unrotated* axis, so the visual fill direction is wrong relative to thumb travel. Default browser thumb is tiny and not skinned for a "lab" aesthetic.
4. **Plunger UI vanishes on Space-press because of the camera-zoom bug.** The user is told to hold Space *and* drag the plunger, but holding Space removes the plunger entirely.
5. **No haptic / audio feedback at the soft stop.** A real pipette gives you a tactile "click" at the soft stop. The sim shows a green dot when you're within `±0.05` of `0.7` — easy to miss while focused on the pipette tip.
6. **Failure modes don't discriminate.** "Drag past soft stop while drawing" should be `HARD_STOP_TO_DRAW` failure. "Eject without reaching hard stop" should be `SOFT_STOP_TO_EJECT` warning (the `rules.test.ts` plan even names these). The current sim only rewards happy-path; it does not teach the soft/hard-stop *technique* the plunger was built to teach.

### 4.2 Alternative A — Two discrete buttons (cheapest, most pedagogically clean)

Replace the slider with two stacked buttons inside the same panel:

- **DRAW (to soft stop)** — pressed-and-held during `INTAKE_SAMPLE`. Releasing while held moves liquid in. Animation shows the plunger sinking to 70% then popping back up.
- **DISPENSE (to hard stop)** — pressed-and-held during `LOAD_WELL`. The button has two press depths visualized: a half-press (soft stop) and full press (hard stop). Need full press to fully eject; half-press fails as `SOFT_STOP_TO_EJECT`.

Pros: matches the verbs ("draw", "dispense") used in lab; eliminates exact-equality float bugs; teaches the soft-vs-hard stop distinction explicitly via two depths on one button; touch-friendly.

Cons: less "physically intimate" than dragging.

### 4.3 Alternative B — Mouse-Y drag on the pipette itself (most diegetic)

When the pipette is lowered (`isLowered=true`), grabbing the pipette body and dragging the *mouse* up/down moves the plunger. The on-screen pipette visibly compresses. No floating slider panel.

- Releasing at the soft stop while drawing → success.
- Drag past soft stop while drawing → `HARD_STOP_TO_DRAW` failure.
- Press to soft stop while ejecting → partial dispense (faint band, `SOFT_STOP_TO_EJECT` warning).
- Press all the way to hard stop while ejecting → full dispense.

Pros: fewest UI elements, most "I'm actually using a pipette" feel, the body is the control (tactile metaphor).

Cons: requires you to fix 2.1/2.2 first (the camera-zoom-loses-cursor problem becomes much worse if drag direction is the input). Trickier on Chromebook trackpads.

### 4.4 Alternative C — Spacebar pressure metaphor (radical, accessible)

Hold Space to lower (today). After lowered, the *duration* of additional Space-hold encodes plunger depth: short hold → soft stop; long hold → hard stop. Visually represented by an in-pipette pressure bar that fills as you hold.

- `INTAKE_SAMPLE`: hold ~600 ms (soft stop), then release → draws.
- `LOAD_WELL`: hold ~1100 ms (hard stop), then release → ejects.
- Overshoot (>1500 ms) in INTAKE → `HARD_STOP_TO_DRAW`.
- Undershoot in LOAD_WELL → partial / failure.

Pros: single key for the entire mechanic; very accessible; nothing to look at except the pipette.

Cons: radically different from a real pipette; no spatial "drag" sensation. Best as an *accessibility-mode toggle* rather than the default.

### 4.5 Recommendation

I'd ship Alternative A as the default and offer Alternative C as an "Accessible mode" toggle. Both eliminate the "drag a rotated slider while also holding a key while also keeping a moving cursor on a target" combinatorial trap. Alternative B is great in principle but compounds with the camera-zoom bug; revisit after 2.1/2.2 are fixed.

Independently of which mechanic ships:

- Add audible click at the soft stop; second click at hard stop.
- Show a *plunger depth diagram* next to the pipette during each action, color-coded green (drew correctly) or red (overshoot/undershoot), persistent for 1 second after the action ends so the user can see what happened.
- Wire `OVERFLOW`, `NO_TIP`, `EMPTY_EJECT`, `SOFT_STOP_TO_EJECT`, `HARD_STOP_TO_DRAW` into the rules layer that `rules.test.ts` already plans for.

## 7. What works well (so the developer doesn't only see red)

- Architecture is clean: `store.ts` is small, `InteractionDriver` is non-rendering and lives at the right level, `usePointerWorld` correctly uses a ref to avoid per-frame re-renders, `targets.ts` keeps world geometry in one place.
- `CLAUDE.md` and `docs/fix-plan.md` exist; the team is thinking in chunks. The `rules.test.ts` `it.todo` scaffold is exactly the right way to plan unimplemented behavior — when you implement the rules layer, you'll have a checklist.
- 3D scene composition (overview camera) is readable: tips on the left, samples in the middle, gel on the right is intuitive lab-bench layout.
- The reset flow (failure → modal → Try Again → store cleared) is correct and works.
- Failure modal styling is clean and unambiguous when it has copy.

## 8. Top 3 fixes I'd ship first

1. **Pin camera lookAt to the current hover target (or the cursor's world point) when zooming**, instead of always `(0,0,0)`. This single change unblocks 2.1, 2.2.2, and 2.3.1, and removes the dominant "klunky" feeling.
2. **Implement the multi-well loop in the rules layer** (`tryEjectIntoWell` → `tryDiscardTip` → `tryPickUpTip` for next sample). This is what `rules.test.ts` already plans for; bring those `it.todo`s online and wire them to `InteractionDriver`.
3. **Rebuild the plunger as Alternative A (two-state DRAW / DISPENSE buttons)** — see §4.2. This eliminates the rotated-slider hack, removes float-equality bugs, and teaches the soft/hard-stop technique explicitly.

After those three, every other P2 becomes much cheaper to fix because the workflow is no longer fighting the user.
